Integration  /  Getting started

Build on Koodify.

Integrate once against Koodify: embed bank-transfer checkout, verify signed webhooks, split payments across zainboxes, and call stable /api/v1 routes with your merchant keys.

✦

In a nutshell
Use pk_… in the browser for checkout. Use sk_… as X-Api-Key on your server for wallet, transactions, settlements, and billing. Prefer the /api/v1/… paths in these guides.

Quickstart

Collect money with inline checkout (pk_…), or read your zainbox from the server with a merchant secret (sk_…). Never put sk_… in client-side code.

01 / CREDENTIALS

Get your keys

After onboarding you receive pk_live_… (browser) and sk_live_… (server). Keep the secret on your backend only.

02 / BASE URL

Point at the API

API host: https://api.koodify.ng. Checkout script: https://js.koodify.ng/v1/koodify-inline.js.

03 / INTEGRATE

Checkout and/or server APIs

Browser: koodifyInitPayment with publicKey. Server: X-Api-Key: sk_live_… for wallet, transactions, settlements, and billing.

NODE.JS · ZAINBOX WALLET 
const zainboxCode = process.env.KOODIFY_ZAINBOX_CODE;

const response = await fetch(
  `https://api.koodify.ng/api/v1/zainbox/${zainboxCode}/wallet`,
  {
    headers: {
      "X-Api-Key": process.env.KOODIFY_SECRET_KEY // sk_live_…
    }
  }
);

const data = await response.json();
// data.data.balances / data.data.virtualAccounts

Authentication

You authenticate with two merchant credentials: a publishable public key for checkout, and a secret key for server APIs.

AUTH publicKey: pk_live_… / pk_test_… Browser checkout
AUTH X-Api-Key: sk_live_… / sk_test_… Server APIs
HMAC X-Koodify-Signature Webhook verification

Environments

Build with test keys (sk_test_… / pk_test_…), then switch to live keys after checkout, webhooks, and (if used) payment splits work end-to-end. Production API host: https://api.koodify.ng.

⌁

Test

Use sk_test_… / test data to validate request handling, webhooks, and error paths.

◉

Live

Use sk_live_… and pk_live_… after your integration is verified.

Inline bank-transfer checkout

Bank transfer popup · publishable public key · temporary VA

Load https://js.koodify.ng/v1/koodify-inline.js and call koodifyInitPayment with amount, txnRef, contact details, callBackUrl, and a publishable public key. Koodify opens a session, shows a one-time virtual account, waits for the transfer, then returns status to your browser callback—and POSTs a signed payment.success event to your callBackUrl even if the tab closed.

JSkoodifyInitPayment(payload, callback)Browser
REQUEST · INLINE CHECKOUT 
<script src="https://js.koodify.ng/v1/koodify-inline.js"></script>
<script>
  koodifyInitPayment({
    publicKey: "pk_live_…",
    amount: "50000",
    txnRef: "FEES_" + Date.now(),
    mobileNumber: "08012345678",
    emailAddress: "parent@example.com",
    callBackUrl: "https://school.example/webhooks/koodify",
    name: "Ada Lovelace",
    customParam: { matric: "ND/12/2211", session: "2026" }
  }, function (response) {
    console.log(response.status, response.reference, response.customParam);
  });
</script>

Virtual accounts

Create static virtual accounts with POST /api/v1/va/create using your merchant sk_… (zainbox is implied by the key). Omit bankType so Adaptive Bank/DVA Routing can choose the rail. Omit bvn, dob, and gender — Koodify fills platform defaults (VA_DEFAULT_*). One-time accounts use POST /api/v1/dva/create with the same merchant key (omit zainboxCode / bankType; accountName is fixed as Zainpay Checkout; duration defaults to 900 seconds and is sent to Zainpay as a number; BVN/DOB/gender are not used on DVA). Inline checkout also issues a temporary VA. Persist the account number and your own customer reference. Optional metadata is stored by Koodify and returned to you. Check balances and history with helpers such as GET /api/v1/va/{accountNumber}.

Payment split

After the customer pays the full amount into a primary zainbox, Koodify can redistribute value to secondary zainboxes. Pick one integration pattern per payment — you do not call both flows for the same checkout. Each share uses either a fixed amount or a percent of the remainder (percents must total 100%). The primary (collector) zainbox must have auto settlement disabled.

i

Two patterns — choose one
A · Ad-hoc split (server-side): send paymentSplit.shares when you initialize payment — no plan endpoint.
B · Reusable plan (browser checkout): create a plan once, then start each payment with only splitPlanId (inline checkout does not accept ad-hoc shares).

Option A — Ad-hoc split on initialize

No plan call. Your backend starts the payment and includes shares in the same request. Use this when shares change per transaction; browser checkout cannot use this path.

POST/api/v1/checkout/initializeServer-side only
REQUEST · CHECKOUT WITH AD-HOC SPLIT 
curl -X POST "https://api.koodify.ng/api/v1/checkout/initialize" \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: $KOODIFY_SECRET_KEY" \
  -d '{
  "zainboxCode": "main_box",
  "amount": "1000",
  "txnRef": "ORDER_889",
  "mobileNumber": "08012345678",
  "emailAddress": "payer@example.com",
  "callBackUrl": "https://merchant.example/paid",
  "paymentSplit": {
    "shares": [
      { "zainboxCode": "tutor_box", "amount": "200" },
      { "zainboxCode": "agent_box", "amount": "50" },
      { "zainboxCode": "main_box", "percent": 100 }
    ]
  }
}'

Option B — Reusable plan + checkout

Call the plan API when you create or update the share recipe. For every payment after that, only start checkout with splitPlanId — do not call PUT /api/v1/split-plans again unless the plan changes.

PUT/api/v1/split-plansOnce (or when plan changes)
REQUEST · CREATE SPLIT PLAN 
curl -X PUT "https://api.koodify.ng/api/v1/split-plans" \
  -H "Content-Type: application/json" \
  -H "X-Api-Key: $KOODIFY_SECRET_KEY" \
  -d '{
  "id": "split_school_fees_v1",
  "name": "School fees — tutor + agent",
  "primaryZainboxCode": "main_box",
  "isActive": true,
  "shares": [
    { "zainboxCode": "tutor_box", "amount": "200" },
    { "zainboxCode": "agent_box", "amount": "50" },
    { "zainboxCode": "main_box", "percent": 100 }
  ]
}'
BROWSER · USE PLAN ID 
koodifyInitPayment({
  publicKey: "pk_live_…",
  amount: "1000",
  txnRef: "ORDER_890",
  mobileNumber: "08012345678",
  emailAddress: "payer@example.com",
  callBackUrl: "https://merchant.example/paid",
  splitPlanId: "split_school_fees_v1"
}, cb);

Webhooks

Signed events · payment.success · verify on raw body

On payment success, Koodify POSTs a signed JSON event to the callBackUrl you set at checkout—even if the browser tab closed. Verify X-Koodify-Signature (hex HMAC-SHA256 of the raw body) using your merchant secret key sk_…—the same key you send as X-Api-Key. Respond with HTTP 2xx quickly, and process asynchronously. Duplicate deliveries are safe to ignore when you key on reference.

POST{your callBackUrl}Merchant endpoint
HEADERS · DELIVERY 
POST /webhooks/koodify/ HTTP/1.1
Content-Type: application/json
X-Koodify-Event: payment.success
X-Koodify-Signature: <hex hmac-sha256 of raw body>
PAYLOAD · payment.success 
{
  "event": "payment.success",
  "status": "success",
  "reference": "ORDER_889",
  "description": "Payment was successful",
  "amount": "1000",
  "currencyCode": "NGN",
  "zainboxCode": "main_box",
  "payer": {
    "email": "parent@example.com",
    "phone": "08012345678",
    "name": "Ada Lovelace"
  },
  "customParam": {
    "matric": "ND/12/2211",
    "session": "2026"
  },
  "paymentSplit": {
    "txnRef": "ORDER_889",
    "status": "success",
    "legs": []
  }
}
VERIFY · SIGNATURE 
// expected = HMAC_SHA256_hex(sk_live_…, raw_body)  // same secret as X-Api-Key
// compare expected to header X-Koodify-Signature (constant-time)
// return 200 OK, then mark the order paid using event.reference

Error handling

API responses use a standard envelope: code, status, description, and data. Treat a payment as successful only when the payment status is explicitly successful (for example success or paid). Reused txnRef values fail checkout—issue a fresh reference for each attempt. On webhooks, verify the signature, acknowledge with 2xx, and ignore duplicates for the same reference.

Security best practices

Keep sk_… on the server only; publish only pk_… in the browser. Merchants need just those two keys: use sk_… for API calls and to verify X-Koodify-Signature on the raw webhook body. Never log API keys, BVN, or other sensitive customer data. Use an HTTPS callBackUrl that accepts POST.
