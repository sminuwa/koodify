Inline checkout

Drop-in bank-transfer checkout. Call koodifyInitPayment to open a modal, show a one-time virtual account, auto-poll for payment, then return payer and (if you passed one) optional customParam on the callback.

Prefer routing through the koodify gateway auth: "gateway" so payer (and optional custom params) are stored and re-attached on status.

Overview

  • Bank transfer only — no card UI.
  • Creates a temporary virtual account for the exact amount.
  • Listens for settlement automatically; merchant can also tap Check Payment Status.
  • Success screen stays open ~10 seconds (or until Done / close).
  • CDN script defaults to https://api.koodify.ng. Checkout uses a publishable publicKey that Koodify maps to the merchant zainbox (Zainpay id stays server-side).

Install

Prefer the hosted CDN (production): 

<script src="https://js.koodify.ng/v1/koodify-inline.js"></script>

For local builds, compile the IIFE from packages/koodify-inline and deploy dist/koodify-inline.js to that CDN path on release. 

cd packages/koodify-inline
npm install
npm run build
# → dist/koodify-inline.js  (upload to js.koodify.ng/v1/)

Exposes global koodifyInitPayment (and KoodifyInline.koodifyInitPayment).

Quick start

koodifyInitPayment(
  {
    amount: "500",
    txnRef: "ORDER_" + Date.now(),
    mobileNumber: "08012345678",
    publicKey: "pk_live_…", // from Koodify seed / dashboard — safe in browser
    emailAddress: "customer@example.com",
    callBackUrl: "https://example.com/webhook",
    name: "Ada Lovelace",
    // optional — omit if you don't need merchant fields
    customParam: {
      matric: "ND/12/2211",
      session: "2026",
      paymentType: "School Fees",
      studentId: "STU001"
    }
  },
  function (response) {
    console.log(response);
    // { status, reference, description, payer?, customParam? }
  }
);
// Script defaults: baseUrl → https://api.koodify.ng
// publicKey is resolved server-side to the merchant zainbox (never expose zainbox)

The function also returns a Promise that resolves on success and rejects on cancel / failure.

Config fields

Field Required Notes
amount yes Naira string. Prefer whole amounts ("500").
mobileNumber yes Stored as payer.phone.
txnRef yes Unique per attempt. Used as koodify operation key.
emailAddress yes Stored as payer.email.
publicKey yes Publishable pk_live_…. Bound to a zainbox in Koodify; safe in the browser.
callBackUrl yes Merchant webhook / return URL passed upstream.
name no Koodify-only. Or payer: { name }. Stripped before Zainpay.
customParam no Optional value-add. Any key/values you want; omit entirely if unused. Alias: customParams.
currencyCode no Default NGN.
bankType no Default gtBank.
logoUrl no Overrides the default Koodify wordmark in the sheet header.
auth no Defaults to "gateway". Use "zainpay" only for direct Zainpay.
baseUrl no Defaults to https://api.koodify.ng. Override for local (http://localhost:8080) or demo proxy.
allowRecurringPayment no Forwarded on init when set.

customParam

Optional

Not required. Checkout works with or without customParam. Use it only when you want to attach merchant-defined fields (matric, order line, campus, etc.) to the payment for your own reconciliation — any keys and values you choose.

When present, Koodify peels it off before calling Zainpay, stores it under transactions.metadata.customParam, and returns it as data.customParam on init / status and on the browser callback. When omitted, those fields are simply absent. 

// with custom fields
"customParam": {
  "matric": "ND/12/2211",
  "session": "2026",
  "paymentType": "School Fees",
  "studentId": "STU001"
}

// or omit customParam entirely — payment still succeeds

Alias: customParams. You can also nest under metadata.customParam on raw gateway POSTs; the inline widget sends top-level customParam.

Callback response

Shape passed to the callback and Promise:

{
  "status": "success",
  "reference": "ORDER_1793402668162",
  "description": "Payment was successful",
  "payer": {
    "email": "customer@example.com",
    "phone": "08012345678",
    "name": "Ada Lovelace"
  },
  "customParam": {
    "matric": "ND/12/2211",
    "session": "2026",
    "paymentType": "School Fees",
    "studentId": "STU001"
  }
}
status When
success Transfer confirmed (auto-close or Done).
cancelled User closed / cancelled before success.
failed Init or hard failure.

Payment flow

  1. POST …/zainbox/card/initialize/payment/inline — session + store payer / customParam.
  2. GET …/zainbox/card/generate-temporary-virtual-account — one-time account for the amount.
  3. Modal shows bank details; UI shows Listening… and auto-polls …/temporary-virtual-account-payment-status every 3 seconds (see below).
  4. On success: confirmation UI (~10s), then callback with status / payer / customParam.

Listening & capacity

Internal · ops

Listening… is short-lived HTTP polling, not a WebSocket or held connection. While the transfer screen is open, the browser calls the status endpoint on a fixed interval until success, cancel/close, or account expiry.

What each poll does

  1. Browser GET {baseUrl}/zainbox/card/temporary-virtual-account-payment-status?txnRef=…
  2. Koodify proxies the same check to Zainpay.
  3. Koodify enriches the response from Postgres (payer / customParam).

Interval is hard-coded in packages/koodify-inline/src/index.js as POLL_MS = 3000. Manual Check Payment Status hits the same route once.

Load estimate

Cost scales with concurrent open checkouts (people sitting on the VA screen), not with total payments completed per day. Rough steady-state:

Open checkouts ≈ req/s to koodify ≈ req/min
1 0.33 20
10 3.3 200
100 33 2,000
1,000 333 20,000

Each poll also hits Zainpay, so upstream volume tracks the same table. An abandoned modal left open for ~15 minutes is ~300 status calls. Polling stops on success, cancel/close, or when the temporary account expires.

When this becomes a problem

  • Many concurrent open modals (campaigns, school fees windows).
  • Zainpay latency or rate limits (often the bottleneck before Axum/Postgres).
  • Not “held TCP connections” — each poll is a normal request/response.

Later levers (if needed)

  • Increase POLL_MS (e.g. 5–10s).
  • Backoff after the first few minutes of listening.
  • Prefer inbound Zainpay webhooks / SSE so the browser does less polling.

Gateway routes used

  • POST /zainbox/card/initialize/payment/inline
  • GET /zainbox/card/generate-temporary-virtual-account?bankType=&e=
  • GET /zainbox/card/temporary-virtual-account-payment-status?txnRef=

Checkout auth: publishable publicKey must match an active zainboxes.public_key; Koodify injects the linked zainbox for Zainpay and never returns that code to the browser. Admin routes use secret GATEWAY_API_KEY. Full catalogue: docs/api.html.

Seed assigns keys: cargo run -p koodify --example seed (prints publicKey=pk_live_… per merchant).
